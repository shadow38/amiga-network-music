  network cut of several seconds with AmiNetXDuo, since the fix of this version." `phase-1-amisqueeze.md:1173`:
  "The most likely cause, not proven"; the WinUAE run with AmiNetXDuo (`:1200-1205`) covered Ctrl-C and the load,
  not a cut; player-16 is 🔶 "the A1200 next" (`README.md:157`); the message of `6d1f562` itself: "the cable cut
  with AmiNetXDuo on the A1200 (player-16) is to confirm it before the release". On the host, no test reaches
  the outcome either (R5).
- failure scenario: 0.8 is tagged at this commit (nothing in "Before the tag" asks for the A1200); if the unproven
  cause is not the whole story, an AmiNetXDuo user still gets stuck after a cut, against the release's own
  CHANGELOG, while its guide says it was never tried.

  consistent); the scoring of the user documentation.

  confirm by the A1200 cable cut.
- suggestion: run the A1200 cable cut before the tag, then update the guide's line and player-16; or reduce the
  CHANGELOG line to what was checked (Ctrl-C, the host's silent server).
- found by: review-plan-compliance (75); review-tests-docs (50 list), merged.

## 5. The 50 list

  real TCP/IP stack; no real `bsdsocket.library`'s internals ever ran on amisqueeze's stack during a measurement.
  `-fstack-usage` shows +40 to 70 B, margins about 10 KB and 15 KB: no failure scenario. review-platform reads
  discovery as a new start-up path (NOT COVERED), review-plan-compliance not (it runs in the main loop). The only

  readings open, and a real TCP/IP stack is a library that runs on amisqueeze's stack without being linked. A

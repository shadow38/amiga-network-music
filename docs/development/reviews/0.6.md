## 3. Findings at 75 or more

**R1. With `QUIET` and no `LOG`, the option errors checked after the log is opened still go nowhere** (score 75)
- dimension: Documentation / Code
- file / line: `src/amisqueeze/amiga.c:734`, then `:739-750`, `:762`, `:773`, and the errors raised in
  `player_main` (invalid `MAC`, `OUTPUT` that cannot be created); `CHANGELOG.md:28-29`;
  `docs/user-guide.md:167`, `:169-170`
- evidence: `wb_quiet = 0;  /* QUIET: from here on, the messages go to the log only */` is set unconditionally,
  with or without `LOG`, before `FLAC=%s: expected AUTO, ON or OFF` (`:740`), `MP3=` (`:744`), `no server` (`:748`),
  `timer.device unavailable` (`:762`), `bsdsocket.library not found` (`:773`). CHANGELOG: "with `QUIET`, an error at
  start-up (a bad ToolType, a log that cannot be opened) opens the window ... until now it went nowhere". Guide
  `:169-170`: "An error in the ToolTypes (an unknown value, a bad number) is shown in the window". Commit `7ac1386`
  checked three icons in WinUAE, all with `LOG=`.
- failure scenario: an icon in `SYS:WBStartup` with `QUIET` enabled and `(SERVER=...)` left in parentheses, or
  `MP3=0N`: no window, no log, amisqueeze quits at boot with nothing shown, which the CHANGELOG says 0.6 fixed.
  With `LOG`, the same errors go to the log only, while the guide says they show in the window.
- rule: method scoring (a statement of the user documentation proven false is 75); A2. The code matches
  `CLAUDE.md` ("except before the log is open") literally; the user documents promise more.
- proven or inferred: proven by reading the order in `main()` (no validation of these values before `:734`); what
  shows on screen to confirm in WinUAE. No host test can cover it (`amiga.c` only).
- suggestion: the cheapest: clear `wb_quiet` after the checks of `main()` (`:773`), which leaves `MAC`/`OUTPUT`
  (checked in `player_main`) silent; or narrow the CHANGELOG and the guide. Clearing it only when a log is open
  would change running behaviour (the first network error would open the window).
- found by: review-tests-docs (75) and review-platform (75), merged.
- seen before: continues 0.4..0.5 R4, marked fixed in the plan (`docs/development/README.md`, 0.6 list).

**R2. Half of the "decoder cannot start" fix is unprotected: `stream.c:340` removed, `make test` stays green**
(score 75)
- dimension: Tests
- file / line: `src/amisqueeze/stream.c:340`; `tests/test_core.c:1638` (`test_decoder_no_start`)
- evidence: `o->dec.out = t->out_fmt;` removed: test_core 403 checks, 0 failed; fake_server 0 failed. `:502`
  copies `o->dec.out` into `t->out_fmt` after each pass, and `:495` computes `full -= full % frame`. A throwaway
  test feeding the skipped track in four pieces on the audio output, without `:340`: `stream.c:495: runtime error:
  division by zero` (UBSan); with it, green and the next track exact. `test_decoder_no_start` runs the virtual
  output only, the skipped track in two pieces.
- failure scenario: a later change drops or reorders `:340`; a track whose decoder cannot get its memory arrives
  in several network reads (the normal case): the next audio pass divides by zero, a trap on the 68k; `make test`
  stays green.
- rule: `CONTRIBUTING.md:11` (tests for core changes); the plan's "Each test seen failing without its fix"; A4
- proven or inferred: proven (planted defect, UBSan).
- suggestion: in `test_decoder_no_start` or an audio twin of it, feed the skipped track in three or more pieces
  with an output tick after each.
- found by: review-tests-docs (75); review-protocol-security noted the audio path read but never run (50).
- seen before: new (the code is new in 0.6).

**R3. The rejection side of the FLAC seek header is never run** (score 75)
- dimension: Tests
- file / line: `src/amisqueeze/flac.c:214-215` (and `:161`); `tests/fake_server.py` (no rejection scenario)
- evidence: `if (!frame_streaminfo(st->head + HEAD_SIZE, 4 + k, b)) fail(st, "cannot start from the middle of this
  file");` replaced by an unconditional use of `b`: test_core 403/0, fake_server 0 failed. `b[34]` is a local
  left uninitialised (`flac.c:190`). The rate-0 fix of 0.6 relies on `:161` for the seek path, untested too.
- failure scenario: a change drops the check at `:214`; after a seek, LMS sends a frame whose header leaves its
  rate or bits to STREAMINFO (code 0): the header is accepted, stack garbage becomes the rate and channel count;
  a rate of 0 brings back the 0.3..0.4 R14 stall through the seek path. `make test` stays green.
- rule: `CONTRIBUTING.md:11`; A4; `CLAUDE.md` (a 75 is fixed or accepted before the tag)
- proven or inferred: proven (planted defect, green).
- suggestion: a unit or fake-server case sending, as after a seek, a frame with rate code 0 (and one with bits
  code 0): expect the message and STMu.
- found by: review-protocol-security (75).
- seen before: 0.4..0.5 R6, not fixed; the plan leaves it "moved to 0.7 or accepted, to decide at the 0.6 review".

**R4. `strm f` stops the track that is playing** (score 75, carried)
- dimension: Code
- file / line: `src/amisqueeze/slimproto.c:242-246` (`case 'q': case 'f': stream_stop(p);`)
- evidence: unchanged in the range. Found by the first replay of 0.3..0.4 (its section 11, "N1"), proven there
  on the player side by a unit test (output STOPPED, ring empty after `strm f` with 0.7 s of track A left).
- failure scenario: LMS sends `f` while playing to drop only the track being streamed (removing, inserting or

- rule: A6

- seen before: 0.3..0.4 N1, not fixed; the plan leaves it "moved to 0.7 or accepted, to decide at the 0.6 review".

**R5. The stack measurement is formally stale: `msg()` now calls deeper** (score 75)
- dimension: Compliance
- file / line: `src/amisqueeze/amiga.c:192-198`, `:214`, `:222`; `CLAUDE.md` (Pitfalls, Stack: "Redo it whenever
  call depth or local variables grow")
- evidence: `msg()` and `msg_raw()` call `quiet_start_message()`, which may call `wb_open_window()` and
  `Open(CON:)`. `-fstack-usage` on the Amiga build: `quiet_start_message` 4 B, `wb_open_window` 8 B, `msg` 28 B;
  `wb_quiet` is 0 from `:734` on, so `Open(CON:)` is never reached from a decoder. The probe (5.6 KB of 16 KB,
  17.8 KB of 32 KB, `a2e132a`) was not redone. The Workbench start's stack was never measured.
- failure scenario: none at these figures (+4 bytes per `msg()` against margins of about 10 and 14 KB); the
  finding is the rule, not an overflow.
- rule: `CLAUDE.md`, Pitfalls, Stack (explicit rule, hence 75)
- proven or inferred: proven (frames measured); the probe needs WinUAE.
- suggestion: accept with the figures above, or rerun the probe from a `Stack 4096` script during the release's
  WinUAE check.
- found by: review-platform (left PARTIAL in its compliance table, raised to a finding in the verification).
- seen before: new.

## 5. The 50 list

- `Makefile:108-110`: the `check-saves` self-test checks what the script reports, not its exit status: with
  `sys.exit(0)` planted, `all` linked binaries holding a planted unsaved `a4` and `make test` stayed green.
- `check-saves.py` misses `movem` loads into d2-d7/a2-a6 from anything but `(sp)+`, and `move.l (sp)+,dN` with no
  matching push (gcc emits such loads only as frame restores today).
- `tests/check-saves.s`: `_bad_postinc` is caught by its plain `move.l 4(sp),a2`, not by `(a2)+`; only
  `_bad_tst_postinc` tests the `(an)+` rule.
- `check-version.py` reads the sources only (names swapped across `#ifdef AMISQUEEZE_FPU` pass; nothing checks the
  strings in `out/`, a committed tree or a `make test` before `dist`); no self-test, and `--release` is not run by
  `make test`.
- Stale comments: `amiga.c:115` ("0 with QUIET"), `:212-213` ("No output ... with QUIET"), `:499` (example
  `0.5`).
- Stale line references in `docs/development/rules.md`: V9, B1, C15 (internal).
- `docs/user-guide.md:128` says an error in the options shows in the window only; with `LOG` some go to the log
  (harmless direction; to fix with R1).
- `mp3.c:27` "15 frames at 320 kbit/s" holds at 44.1 kHz only (11 at 32 kHz, 17 at 48 kHz); nothing relies on it.
- CHANGELOG: the README quick-start rewrite (`dec3197`, `f97fab8`) is not listed.
- The "tested with 3.0, 3.1, 2.04" claim is recorded in a commit message only, not in `docs/development/`.
- The real decoders' "not enough memory" paths (`flac.c:288-292`, `mp3.c:129-132`) cannot be made to fail by the
  stub; never run.
- Before 0.6: a request over 1 KB is refused after STMf is sent, with no STMn or DSCO; LMS's reaction unchecked.
- Before 0.6: under `QUIET`, a log write error (`amiga.c:140-143`) is reported nowhere.
- Internal: the Decisions tables of the two acceptance reports are left empty; the fate of their findings is in
  the plan's 0.6 list (`docs/development/README.md:101-114`).

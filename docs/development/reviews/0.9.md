## 3. Findings at 75 or more

**R1. `strm f` after a refused or failed next stream drops the previous, fully received track** (score 75)
- dimension: Code
- file / line: `src/amisqueeze/stream.c:100` (`stream_flush`), `:107-115` (`stream_abandon`);
  `src/amisqueeze/player.h:310-311`
- evidence: `stream.c:100` `t = &o->queue[--o->queued];         /* the track the last strm s queued */`;
  `player.h:310` "strm f: drops the track being streamed (the last one queued)". `stream_abandon()` (from `refuse()`
  with autostart 2 or 3, the `STREAM_REFUSED` state new in 0.9, and from `stream_fail()`, DSCO) pops the last
  `strm s`'s entry when it has no data, so `queue[queued-1]` becomes the track before it, whose stream ended
  (`STMd` sent). `protocol.md:97`: "`strm f` drops only the last queued track".
- failure scenario: A plays; B fully received (`STMd` sent, queued 1); `strm s` C answered 404 with autostart 3 (or
  C's connection fails, DSCO); then `strm f`: queued 0, B's data truncated from the ring, no `STMs` for B. B is
  silently never played and the server never hears of its start. A unit probe of the agent (A 50,000 bytes, B
  20,000) gave an `OUTPUT` file of 50,000 bytes instead of 70,000 and the trace `STAT:STMu`.
- rule: A2 (a comment stating the invariant `stream_flush` relies on, false); `protocol.md:97`.
- proven or inferred: proven in the code (read again; the agent's probe in its worktree); to confirm: that LMS sends
  `strm f` in that window (the playlist edited after a failed next track), in WinUAE. Music Assistant follows `strm
  f` with `strm q`, so it does not matter there. 50 if LMS never does.
- suggestion: remember whether the last `strm s`'s entry is still queued (a flag cleared by `stream_abandon`) and
  leave the queue alone in `strm f` when it is not; add the probe as a test.
- found by: review-protocol-security (75).
- seen before: new (the `REFUSED` path is new in 0.9; the DSCO path before 0.9).

**R2. A `strm s` that replaces a stream still connecting, reading headers or waiting for `cont` leaves the
replaced track's empty entry: two `STMs` back to back, a slot of the 16 lost** (score 75)
- dimension: Code
- file / line: `src/amisqueeze/stream.c:147`, `:163-168` (`stream_start`)
- evidence: `stream.c:147` `stream_close(p);                    /* a stream still running is abandoned */`;
  `stream_close()` (`:48-55`) only closes the socket. Unlike `stream_abandon()` (`:113-114`), the replaced track's
  entry is not dropped; the new entry gets the same start (`ring.total_in`). The header comment (`:13`): "STMs is
  sent again when the output reaches it".
- failure scenario: A plays; `strm s` B (autostart 3) is connecting, or has its headers and waits for `cont`; then
  `strm s` C. Queued 2, both starting at the same position; at the boundary the trace is `STAT:STMs STAT:STMs
  STAT:STMu` (agent's probe). C plays right; the server gets a `STMs` for a track it replaced, and the empty entry
  counts toward `MAX_TRACKS`. In 0.9 the wait for `cont` has no time limit, so with Music Assistant (which re-queues
  and sometimes never sends `cont`, `README.md:143`) the window is unbounded; in 0.8 it was only `CONNECTING` and
  `HEADERS`.
- rule: `protocol.md`, A track's life (one `STMs` per track started); A2 (`stream.c:13`).
- proven or inferred: proven in the code (read again, `stream_close` included; the agent's probe); to confirm: what
  LMS and Music Assistant do with the extra `STMs`, and whether a server replaces a stream before `STMd` or `cont`,
  in WinUAE. 50 if no server ever does.
- suggestion: in `stream_start`, after `stream_close()`, drop the last entry when it holds no data and the previous
  stream was `CONNECTING`, `HEADERS` or `CONT` (as `stream_abandon` does); add a test.
- found by: review-protocol-security (75).
- seen before: new (widened by 0.9's `CONT` state).

**R3. Under `Run >NIL:`, a command-line error is written to `NIL:` and lost: no window, a silent exit** (score 75)
- dimension: Code (platform) / Documentation
- file / line: `src/amisqueeze/amiga.c:835-836`, with `:798-799` and `:919-920`; `docs/user-guide.md:318-319`;
  `docs/development/architecture.md:264`
- evidence: `amiga.c:835-836` `else if ((rda = ReadArgs(TEMPLATE, args, NULL)) == NULL)` /
  `PrintFault(IoErr(), "amisqueeze");`. Into `NIL:`, `window_start()` only calls `win_begin(DEFAULT_WINDOW, 2)`
  (`:798-799`), which neither opens the window nor selects an output (`:273-289`): the window opens at the first
  `msg()` (`win_show`, `:203-225`). `PrintFault` writes to `Output()`, `NIL:`. Guide: "with `QUIET`, or `Run >NIL:`,
  it stays closed, unless an error comes at start-up"; `architecture.md:264`: "A message during start-up opens it".
  The ToolTypes path already goes through `msg()` (`parse_line`, `Fault()` at `:723`).
- failure scenario: `S:User-Startup` holds `Run >NIL: amisqueeze NAME=Kitchen UNIT=x`, or a mistyped keyword:
  `ReadArgs` fails, the message goes to `NIL:`, amisqueeze exits with RC 20, nothing is shown and the player never
  appears on the server.
- rule: `code-rules.md:51` (messages go through `msg()`); `CLAUDE.md` (no `printf`, `Printf` or `PutStr` called
  directly: `PrintFault` is their kin); the scoring of the user documentation (a statement proven false).
- proven or inferred: proven by reading (a fixed path; Amiga only, not run).
- suggestion: `Fault()` into a buffer and `msg("amisqueeze: %s\n", ...)`, as `parse_line()` does.
- found by: review-platform (75).
- seen before: new (the `NIL:` window is new in 0.9; before it, `PrintFault` into `NIL:` was the expected
  behaviour).

**R4. The message "this window cannot be hidden" is not in the user guide, which says Hide always closes the
window** (score 75)
- dimension: Documentation / Compliance
- file / line: `src/amisqueeze/amiga.c:243-244`; `docs/user-guide.md:315` and the Messages section
- evidence: `amiga.c:244` `msg("amisqueeze: this window cannot be hidden (error %ld)\n", (long)IoErr());`, shown
  without `VERBOSE` when the console refuses `ACTION_FORCE` (the comment at `:233-234` names "a replacement of
  CON:"); guide `:315` "**Hide Interface** closes it. Its close gadget does the same."; the message is in no user
  document (0 hits), only in the plan (`phase-1-amisqueeze.md:1316`).
- failure scenario: a user whose `CON:` is replaced by a console handler that refuses `ACTION_FORCE` selects Hide in
  Exchange: the window stays and shows the message; the guide says Hide closes it and lists no such message.
- rule: `CLAUDE.md` (each user-visible change: the user guide updated); `documentation-rules.md` (the guide answers
  every option, message and limit); `CONTRIBUTING.md`, Proposing a change.
- proven or inferred: the omission proven; that a console replacement in use refuses `ACTION_FORCE` is inferred (none
  was tried): 50 if none does.
- suggestion: a row in the guide's Messages (what it means: the console cannot end its pending read; close the
  window with its gadget or Ctrl-C), and qualify the line at `:315`.
- found by: review-plan-compliance (75), review-tests-docs (75), merged.
- seen before: new.
